# CLAUDE.md — бот мониторинга сервера

Памятка для Claude Code, чтобы продолжать проект без повторных вопросов. Пользовательская документация —
в `README.md` (и `README.en.md`); здесь — то, что нужно разработчику: устройство, правила, решения и история.

## Правила работы (важно)

- **Общение и тексты — по-русски.** Строки интерфейса в коде тоже пишутся по-русски (см. «Язык»).
- **Ничего не ставить и не менять на серверах и ПК без явной команды пользователя.** Сначала код и PR,
  выкладка — только когда пользователь сам скажет («выкладывай <sha> на Hetzner…»). Короткое «да» защита
  Remote Control не принимает — нужна фраза пользователя с сутью действия.
- Подтверждения для действий на ПК/серверах пользователь пишет прямо в ветке, где идёт работа.
- **Секреты в репозиторий не попадают.** Токен Telegram пользователь вписывает в `config.yaml` сам и в чат
  не присылает. `config.yaml`, `settings.json`, `state.json`, `*.db`, `Backups/`, `deploy/pc/pull-backups.json`
  — в `.gitignore`. Репозиторий **публичный**: не писать в код, README и этот файл IP-адреса, хосты и chat_id.
- Пользователь часто сам мержит PR. Ветки для работы — `claude/...`, в `main` напрямую не пушить.
- Не оставлять запускаемые копии сервисов после переезда (урок 2026-11-24: старый alerts_bot случайно подняли
  на старом сервере).

## Что делает проект

Telegram-бот (Python, `python-telegram-bot` 22 с job-queue, `psutil`, `PyYAML`, `matplotlib`) следит за сервером:
CPU/RAM/swap/диски/температура/inode, службы systemd, процессы, контейнеры Docker (перезапуски, unhealthy,
ошибки в логах), внешние проверки (HTTP/SSL/TCP/ping/DNS), безопасность (входы SSH с новых IP, подбор пароля,
автобан через ufw, новые открытые порты, обновления пакетов), бэкапы (своя копия, свежесть чужих, выгрузка на ПК,
проверка восстановимости), история метрик и графики, журнал инцидентов и недельный отчёт, действия из Telegram
с подтверждением (перезапуск, kill, очистка места, установка обновлений, перезагрузка, обновление самого бота
с откатом). Один бот следит и за **вторым сервером** через ограниченного SSH-агента.

Управление — кнопками (постоянная клавиатура + inline-меню «Настройки») и командами:
`/status /procs /mem /services /servers /alerts /incidents /settings /logs /chart /probe /backup /net /updates
/ban /actions /mute /unmute /maint /lang /name`.

## Инфраструктура (без адресов)

- **Главный сервер — Hetzner** (Ubuntu 26.04, Python 3.14). Бот в `/opt/monitor_bot` (код и `venv` принадлежат
  root), служба `monitor-bot.service` от пользователя `monitor`, данные в `/var/lib/monitor_bot`
  (`StateDirectory`): `settings.json`, `state.json`, `metrics.db`, `metrics-ИМЯ.db`, `actions.log`, `backups/`,
  ключ `remote_ed25519` и `known_hosts` для второго сервера. На Hetzner также живёт отдельный `hetzner-bot`
  (systemd, свой git-репозиторий, за ним бот следит через `log_services`).
- `monitor` **не в группе docker** (она равна root) и имеет sudo **только** на `/usr/local/sbin/monitor-bot-action`
  (`deploy/sudoers-monitor-bot`). Состоит в `systemd-journal` (чтение журнала sshd и служб).
- Файлы помощника на сервере: `/etc/monitor-bot/allowed-services`, `/etc/monitor-bot/backup-watch`,
  `/etc/monitor-bot/update-repo`; результаты `/run/monitor-bot-update.json`, `/run/monitor-bot-apt.json`;
  отметки выгрузки на ПК `/var/lib/monitor-bot-offsite/status.json`.
- **Второй сервер — OVH** (имя в боте `ovh`, Ubuntu 26.04). На нём `weather-bot` (git-клон, бэкап 03:30 UTC,
  свой сторож в cron) и `alerts_bot` (контейнер `alerts_bot-bot-1`, бэкап `bot.db` 03:35 UTC). Там: вход только
  по ключу, ufw (только SSH), fail2ban (главный сервер в `ignoreip`), Docker. Бот заходит туда ключом, который
  в `authorized_keys` ограничен `command="/usr/local/sbin/monitor-agent",restrict`. Агенту разрешено
  перезапускать только службы из `/etc/monitor-agent/allowed-services` (cron, docker, containerd).
- **ПК пользователя (Windows)**: код в `D:\Program\prg_py\Monitor_bot`. Задача планировщика `monitor-bot-pull`
  утром забирает копии с Hetzner в `D:\Program\Backups\server` и напрямую с OVH в `D:\Program\Backups\ovh`
  (ключ `monitor_bot_pull`, на серверах ограничен командой `pull-stream`).
- Внешний контроль «сервер жив» — `heartbeat_url` (healthchecks.io).

## Запуск и тесты

```
python -m venv venv && venv/bin/pip install -r requirements.txt
cp config.example.yaml config.yaml     # вписать token и allowed_chats (chat_id бот покажет на /start)
python bot.py config.yaml
python -m unittest discover tests      # сейчас 254 теста, ~25 с
```

Правила для тестов (выучены на ошибках):
- Тесты гоняются и **на сервере при обновлении, внутри службы `monitor-bot-update-*.service`**: тест не должен
  зависеть от своей cgroup/юнита, от того, что он запущен из-под systemd.
- Тесты **не читают настоящие файлы сервера** (`/run/monitor-bot-update.json`, `/run/monitor-bot-apt.json`,
  `/etc/monitor-bot/*`), **не вызывают настоящий помощник** и **не ходят в сеть** — всё мокается.
- Новая строка интерфейса → обернуть в `_()` и добавить перевод в `locales.py` (UK и EN), иначе упадёт
  `test_i18n`. Подстановки `{name}` должны совпадать.

## Как выкладывается

Две части с разными правами:

1. **Код бота** — штатно кнопкой «Настройки → ⬆️ Обновление бота» (или пользователь говорит «выкладывай <sha>»).
   Помощник `update SHA` в отдельной службе systemd: проверяет, что коммит есть в `main`, скачивает архив,
   гонит тесты от `monitor`, сохраняет `/opt/monitor_bot.bak-update-ДАТА`, ставит код (без `config.yaml`
   и `venv`), обновляет зависимости только wheel-пакетами, перезапускает и через 30 с проверяет; при сбое
   откатывает. При выкладке алерты о перезапуске своих служб не шумят (тишина при деплое).
2. **Помощник, агент, sudoers, юнит** — **никогда автоматически** (чтобы код с GitHub не расширил права бота).
   Только вручную после явного согласия пользователя: копия старого файла (`*.bak-<метка>`), затем
   `install -o root -g root -m 755 …`. Бот сам пишет, если они устарели.

Как это делалось из Claude Code: Remote Control-сессия на ПК пользователя → `ssh` на сервер. Авторежим Claude Code
на ПК **блокирует замену root-помощника и изменяющие ssh-команды** — нужно ручное подтверждение в RC-сессии
с фразой пользователя о сути действия. Ручная выкладка кода: копия `/opt/monitor_bot` в `.bak-*`, архив
`codeload.github.com/.../tar.gz/<sha>`, копирование кода без `config.yaml`, тесты от `monitor`, рестарт.

Если PR меняет `deploy/monitor-agent`, агент на OVH ставится отдельно тем же ручным способом
(копия `/usr/local/sbin/monitor-agent.bak-<метка>`).

## Принятые решения и почему

- **Docker только через помощник** (`docker-poll`, `docker ARGS` в жёстких видах), `monitor` не в группе docker:
  группа docker = root.
- **sudo только на один помощник**, который сам валидирует аргументы; перезапуск только служб из allowed-services,
  ssh не перезапускается; kill не трогает системные процессы, apt/dpkg и само обновление.
- **Второй сервер — через агента с `command=…,restrict`**, а не обычный SSH: по ключу нельзя получить оболочку.
  Автобан там делает **fail2ban**, а не главный бот: работает, даже если главный сервер недоступен.
- **Бэкапы забирает ПК сам** (pull, ключ только на `pull-stream`): если сервер пропадёт, копии не пропадут, а на
  ПК не нужно ничего открывать. С OVH ПК забирает **напрямую** (пересылка через Hetzner убрана в PR #38).
- **Автобан + ручной бан** (ufw, правила с пометкой `monitor-bot`): 10 попыток за 10 мин → 24 ч. Считаются и
  `[preauth]`-попытки (перебор ключей); щадятся только реальные открытые SSH-сессии, IP с успешным входом за
  30 дней и `autoban_whitelist`. Ручной бан — постоянный.
- **Swap не нужен** (решение пользователя).
- **Тихие часы 23:00–06:00**: ночью только критичные алерты. Режим обслуживания `/maint` глушит всё.
- **Языки RU/UK/EN**; русский — исходник в коде, переводы по русскому ключу.
- **Имя сервера** — `server_name` в config.yaml и `/name` (переименование в панели хостинга hostname не меняет).
- **Обновления пакетов** из бота: phasing-пакеты Ubuntu показываются «⏸ отложено» и не идут в «Установить все»;
  после установки список перечитывается. **Одно окно обновлений** для своего и удалённого сервера.
- Карточка Hetzner и карточка OVH устроены одинаково (службы, входы SSH за час, «Заблокировано ботом», порты).
- Монитор на Hetzner следит за всеми контейнерами (`containers_auto`); удалённый авто-контейнер, который убрали,
  — не авария (PR #40).
- Служба посреди перезапуска — не падение: переходные состояния перепроверяются (PR #32).
- Вход по SSH с IP GitHub Actions ключом деплоя (`deploy_keys`) после мержа в weather-bot/alerts_bot — ожидаем,
  это «🚀 Деплой», а не взлом.

## Известные проблемы и особенности

- `cloud-init-main`/`cloud-final` на Hetzner падают после каждой перезагрузки — безвредная гонка с
  переименованием сетевой карты в netplan. Пользователь выбрал только `systemctl reset-failed`, отключать
  cloud-init не разрешал.
- Docker обходит ufw для опубликованных портов: бан по IP не закрывает `-p`-порты контейнеров (нужен `DOCKER-USER`
  или публикация на 127.0.0.1).
- Сбои связи с Telegram 18–19.11 и 23.11 были на стороне Telegram/аккаунта, не бота.
- Если упадёт весь главный сервер, бот ничего не пришлёт — для этого `heartbeat_url`.
- Со старым помощником новые кнопки отвечают «помощник на сервере не обновлён» — это значит, что после мержа нужна
  ручная замена помощника.
- `bot.py` и `locales.py` большие (по ~2 тыс. строк): ищите по имени обработчика/строки, а не читайте целиком.
